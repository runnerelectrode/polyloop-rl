## The sampler crash, diagnosed from code

"RPC call to sample_tokens timed out" is vLLM 0.26.0's multiproc-executor RPC timeout (`vllm/v1/executor/multiproc_executor.py:392`, deadline `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS`); our engine log showed that executor. It means a GPU worker hung after the weight sync. Our node ran Megatron + LoRA with `merge_lora=False` (set in serve.sh; SkyRL's default is True), which takes the in-place `load_lora_adapter` branch in `worker_dispatch.py:657-662` (its comment says "no need to pause"; the Megatron export is `_save_lora_adapters_and_sync`, `megatron_worker.py:1400-1459`), while up to `SKYRL_GENERATE_CONCURRENCY_PER_ENGINE` (default 512, `skyrl/env_vars.py:53`) requests were in flight with ~10k-token prompts. The first adapter load (the warm-up save) was fine; the second, with trained weights and a full batch in flight, hung. Miles pauses generation (`--pause-generation-mode retract` default: requeue, flush cache, bump version); ART never syncs into running requests (new adapter name per step, or CAS-guarded slot with leases). A second hypothesis to rule out: vLLM 0.26 LoRA bugs on Qwen3.5 GatedDeltaNet layers (issues #47639, #36372, #38085); check which modules Megatron-Bridge's `all-linear` mapping exports for the GDN layers.

Fix to try first: `SKYRL_GENERATE_CONCURRENCY_PER_ENGINE=8`, and call `pause_generation` / `resume_generation` (`remote_inference_client.py:1015-1021`; they wrap vLLM `/pause?mode=keep`, and `PauseMode` also has ABORT and WAIT) around `save_weights_for_sampler`. Alternative that needs no pause: load each cycle's adapter under a new name and switch the proxy's `model=` (ART's step_lora mode).
